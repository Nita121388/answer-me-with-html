A

结论
差距在哪

布局引擎、图形语义、查看交互三层都不够。不是排版不好看，是画不了架构图最常见的结构。

  • 布局：dagre 只有一层分组，没有嵌套边界、端口和正交绕行。
  • 语义：只有 4 种形状，没有云、队列、人物，也没有图标。
  • 交互：查看器只有缩放和平移，没有聚焦与路径追踪。

处方：不换产品路线。模型仍写关系，CLI 仍算坐标。分层内核补上 ELK，语法层新增 arch，交互做成渐进增强。

B

差距清单（实测）

先看现状。下面是 flow 今天真实的边界。

架构图常见需求 现状 证据
嵌套边界（VPC > 子网 > 服务） 不支持 VPC 组和 Subnet 组重叠时，节点被后一个组带走，边界画错
端口与锚点（A.e -> B.w） 不支持 冒号成了节点名的一部分
双向与无向边（A <-> B、A -- B） 不支持 整行被当成一个节点，不报错
云、队列、人物、负载均衡等形状 只有 rect / round / diamond / db 四种 am help flow
图标 无 节点只能靠文字
分层泳道（同层强制对齐） 无 dagre 的 rank 不可控制
边绕开障碍物 靠换方向 官方建议是改 TB/LR 或拆图
未识别语法 静默生成错误节点 Gateway <-> Service 渲染成一个节点

最后一条最伤。模型写错语法时，CLI 不给行号，图直接画歪。这和项目"出错带行号和改法"的卖点相反。

C

选型：成熟项目怎么解决
项目 怎么解决 许可与依赖 适合 am 吗
ELK（elkjs 0.12） 分层布局内核：嵌套节点、端口、正交路由、边标签 EPL-2.0，约 8 MB，纯 JS 是。补的正是 dagre 缺的内核能力
D2 容器嵌套、图标、cloud 形状、near 提示、sketch 风格 MPL-2.0，Go 二进制 内核也用 ELK。语法可借鉴；二进制不适合做默认
Graphviz (dot) cluster 嵌套、罗盘端口、ortho 样条 EPL，C 或 wasm 语义值得抄；视觉老派，wasm 体积大
Mermaid subgraph 嵌套、30 多种形状、architecture-beta MIT，浏览器运行时 只能做语法兼容参考。运行时渲染和单文件离线相冲，C4 图自身已停止维护
React Flow / Cytoscape 运行时交互图库 MIT，JS 包 否。基础视图必须无 JS 可读
Structurizr / C4 语义模型，按 Context / Container / Component 取视图 开源 二期可做语义层，一期不必
Archify 聚焦、路径追踪、搜索、演示模式 独立产品 交互目标对齐。这是差距的直接参照

结论：内核选 ELK，语法借鉴 D2 与 Graphviz，兼容层对齐 Mermaid，交互对齐 Archify。

分阶段路线图
阶段 内容 验收
P0 收敛失败 未知箭头与形状报错带行号；建立 3 张参考图用例集（云三层、k8s、事件驱动） 错误语法 100% 报错，不再静默画歪

工期估计：P0 约 1 周，P1 约 3 周，P2 约 2 周，P3 约 2 周。P0 和 P1 可并行。

F

风险与边界
ELK 体积
8 MB 解压，EPL-2.0 双许可
dagre 保留
简单图更快，回退保底
图标来源
自绘通用几何图标，不内嵌云厂商商标
运行时依赖
不引入任何浏览器图库，基础视图无 JS
语法分裂
arch 与 flow 共用一个解析器，一套心智

三条不做的：不做运行时图库。不做联网拉图标或导入。不做自动发现架构。

最后一点建议：先做 P0。哪怕后面全砍掉，把"静默画歪"改成"报错带改法"，架构图的可信度就先回来了。这也是项目自己的验收哲学：行号、示例、一句话改法。
